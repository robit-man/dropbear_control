# Exact-model plant parameter-set assembly

Status: implemented offline, positive-capable, real baseline blocked.

This stage is the sole bridge from reviewed product-source facts to a
qualified exact plant set. It performs deterministic assembly; it does
not interpret source documents, select among competing facts, infer a family
default or establish protocol applicability.

## Evidence flow

```text
pinned product PDF
  -> page/table candidate
  -> extractor submission
  -> independent fact-review event
  -> active V2 source fact
                                      \
                                       -> exact parameter-set materializer
                                      /
installed tuple + protocol source
  -> independent applicability decision

exact materialized set
  -> reviewed execution profile
  -> exact V1 or V2 runtime adapter contract
  -> aggregate plant registry V4 as sourced/loadable only when one contract exists
  -> simulator runtime catalog
  -> exact-model actuator SIL eligibility
```

Revoking or superseding a source fact or removing the accepted applicability
decision changes the assembly generation and removes the affected set. A
source-only plant remains simulation evidence: it never grants motor support,
physical I/O or motion authority.

## Admission invariants

One model/tuple may materialize a qualified source set only when all of these
are true:

1. exactly one active accepted fact exists for each of 34 parameter fields;
2. exactly one active accepted fact exists for each of four operating-envelope
   fields;
3. parameter observations are scalar and envelope observations are ranges;
4. every normalized value and range is inside its reviewed SI uncertainty;
5. source operating voltage, ambient temperature and direction conditions fit
   the assembled envelope;
6. speed and torque ranges establish the same rotation direction;
7. efficiencies, inertias, electrical constants, stiffness, thermal constants,
   loop periods and physical maxima satisfy closed semantic constraints;
8. the envelope stays inside selected speed, torque and temperature limits;
9. at least one active, independently accepted exact protocol-applicability
   decision exists for the same model; and
10. every generated byte remains bound to the upstream registry generations,
    fact hashes, decision IDs and materializer hash.

Accepted applicability decisions with the same seven-field tuple coalesce into
one set. Different exact tuples materialize distinct sets. No "latest", family,
model-only or first-match selection exists.

## Controlled outputs

- `generated/myactuator/plant/parameter_sets/registry.json`
- `generated/myactuator/plant/parameter_sets/sets/<plant-id>.json`
- `generated/myactuator/plant/runtime_adapters/registry.json`
- `generated/myactuator/plant/runtime_adapters/contracts/<contract-id>.json`
- `generated/myactuator/plant/runtime_adapters_v2/registry.json`
- `generated/myactuator/plant/runtime_adapters_v2/contracts/<contract-id>.json`
- `generated/myactuator/plant/runtime_registry.json`

The assembly registry covers all 44 catalog models even when blocked. Each
model lists exact missing fields, accepted decision IDs, active source-fact
IDs, materialized plant IDs and blockers.

The old `assets/myactuator/plant_parameter_sets/*.json` intake is retired.
Plant registry V4 consumes only the transactionally generated file sets and
rechecks its registry/file hashes. The assembler emits
`runtime_loadable=false`, `runtime_adapter_id=null` and the
`runtime_plant_adapter_missing` blocker. A separate V1 or V2 adapter removes
that blocker only after an independently reviewed exact execution profile
supplies the solver/scenario choices that are not motor source facts. All 38
source semantics must be accounted for. V1 rejects unrepresentable semantics;
V2 represents the extended timing/noise/torque/direction set. Two active
adapter generations for one plant deny rather than invoking precedence. See
`docs/PLANT_RUNTIME_ADAPTER.md` and
`docs/PLANT_RUNTIME_ADAPTER_V2.md`.
